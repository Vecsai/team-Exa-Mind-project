# Роли и ответственность в команде

## Введение

Данный документ описывает распределение ролей между участниками команды
и их зоны ответственности при работе над проектом. Распределение основано
на результатах первой самостоятельной работы и учитывает сильные стороны
каждого участника.

---

## Состав команды и роли

### 1. Руководитель разработки ПО

**Зона ответственности:** общая координация проекта, управление репозиторием,
контроль сроков.

**Обязанности:**
- Создание и настройка командного репозитория на GitHub.
- Добавление участников в Collaborators.
- Контроль соблюдения структуры репозитория.
- Проверка и слияние (merge) Pull Request'ов.
- Сборка итогового отчёта по самостоятельной работе.
- Разрешение спорных ситуаций в команде.
- Связь с преподавателем.

**Обоснование выбора:** участник с этой ролью обладает навыками организации
работы в команде и несёт основную ответственность за результат проекта.

---

### 2. Архитектор ПО

**Зона ответственности:** техническая структура репозитория, правила
ветвления, вспомогательные скрипты.

**Обязанности:**
- Настройка файла `.gitignore`.
- Описание структуры каталогов и правил именования веток.
- Проверка технических Pull Request'ов.
- Помощь руководителю при слиянии веток.
- Контроль за отсутствием служебных файлов в репозитории.

**Обоснование выбора:** участник понимает принципы организации проектов
и может обеспечить техническую чистоту репозитория.

---

### 3. Программист

**Зона ответственности:** исходный код проекта в каталогах `src/`.

**Обязанности:**
- Написание исходного кода в `practical-works/*/src/`.
- Создание осмысленных коммитов по коду.
- Создание Pull Request'ов на свои изменения.
- Реагирование на замечания ревьюеров.
- Поддержание кода в актуальном состоянии.

**Обоснование выбора:** участник владеет навыками программирования
и может реализовать техническую часть проекта.

---

### 4. Специалист по тестированию

**Зона ответственности:** качество результатов, тестовые сценарии,
проверка Pull Request'ов.

**Обязанности:**
- Проверка корректности Pull Request'ов других участников.
- Написание тестовых сценариев и планов тестирования.
- Ревью изменений, связанных с качеством.
- Фиксация найденных ошибок в комментариях к PR.
- Подтверждение готовности изменений к слиянию.

**Обоснование выбора:** участник внимателен к деталям и способен
объективно оценивать качество работы.

---

### 5. Специалист по данным

**Зона ответственности:** данные, датасеты, скрипты обработки данных.

**Обязанности:**
- Подготовка и загрузка данных в репозиторий.
- Написание скриптов обработки данных в `scripts/`.
- Создание коммитов по данным и скриптам.
- Создание Pull Request'ов.
- Контроль актуальности данных.

**Обоснование выбора:** участник имеет опыт работы с данными
и инструментами их обработки.

---

### 6. Исследователь

**Зона ответственности:** теоретическая часть проекта, документация,
аналитика, RACI-матрица.

**Обязанности:**
- Заполнение `docs/roles-and-responsibilities.md`.
- Заполнение `docs/raci-matrix.md`.
- Написание теоретической части отчётов.
- Сбор и анализ источников.
- Ревью текстовых частей Pull Request'ов.
- Формулирование выводов по работе.

**Обоснование выбора:** участник умеет работать с информацией,
анализировать и структурировать материал.

---

## Принципы взаимодействия

1. **Один ответственный за задачу.** По каждой задаче есть один
   ответственный (Accountable) — как правило, руководитель.
2. **Работа только через ветки.** Никто не пишет напрямую в `main`.
3. **Обязательное ревью.** Каждый Pull Request проверяется другим участником.
4. **Осмысленные коммиты.** Сообщения коммитов отражают суть изменения.
5. **Актуальность.** Перед началом работы участник обновляет локальный `main`.

---

## Заключение

Распределение ролей учитывает сильные стороны участников и обеспечивает
покрытие всех этапов работы: от планирования и организации до разработки,
тестирования и документирования. Такое распределение позволяет каждому
участнику внести видимый вклад в общий результат.
