## 1. Теоретическая часть

### 1.1. Что такое система контроля версий

Система контроля версий (Version Control System, VCS) — это программное
обеспечение, которое позволяет хранить историю изменений файлов, отслеживать
авторство правок и организовывать совместную работу над проектом.

Наиболее распространённой распределённой системой контроля версий является
**Git**. Git хранит полную историю изменений локально у каждого участника,
а также позволяет синхронизировать её с удалённым репозиторием.

### 1.2. Что такое репозиторий

**Репозиторий** — это хранилище проекта, в котором содержатся все файлы,
папки и история изменений. Репозиторий может быть:

- **локальным** — находится на компьютере участника;
- **удалённым** — размещён на платформе (GitHub, GitLab, Bitbucket).

В рамках командной работы используется **единый удалённый репозиторий**,
к которому подключаются все участники. Это позволяет:

- хранить все материалы проекта в одном месте;
- отслеживать вклад каждого участника через историю коммитов;
- организовать проверку изменений через Pull Request;
- избежать потери данных.

### 1.3. Основные понятия Git

- **Коммит (commit)** — зафиксированное изменение в репозитории.
  Каждый коммит имеет автора, дату и сообщение.
- **Ветка (branch)** — отдельная линия разработки. Позволяет вести работу
  параллельно, не мешая другим участникам.
- **Основная ветка (main/master)** — стабильная версия проекта.
  Сюда попадают только проверенные изменения.
- **Pull Request (PR)** — предложение внести изменения из своей ветки
  в основную. Позволяет провести ревью и обсуждение.
- **Merge** — слияние веток. Обычно выполняется после одобрения PR.
- **Ревью (review)** — проверка изменений другим участником команды.

### 1.4. Модель командной работы через Git

В рамках проекта используется следующая модель:

1. **Один общий репозиторий** на GitHub.
2. **Каждый участник работает в своей ветке** (`feature/...` или `role/...`).
3. **Изменения вносятся через коммиты** с осмысленными сообщениями.
4. **Pull Request** создаётся для проверки изменений.
5. **Ревью** выполняется другим участником команды.
6. **Merge** выполняет руководитель после одобрения.
7. **Основная ветка `main`** всегда содержит стабильную версию проекта.

Такая модель обеспечивает:

- изоляцию работы участников;
- прозрачность вклада каждого;
- контроль качества через ревью;
- сохранность истории изменений.

### 1.5. Преимущества использования Git в команде

1. **История изменений.** Можно посмотреть, кто, когда и что изменил.
2. **Параллельная работа.** Участники не мешают друг другу.
3. **Откат изменений.** Можно вернуться к предыдущей версии.
4. **Проверка через ревью.** Изменения попадают в `main` только после проверки.
5. **Распределённость.** У каждого есть полная копия репозитория.
6. **Интеграция с платформами.** GitHub предоставляет удобные инструменты
   для работы с PR, issues, проектами.

### 1.6. Роль Git в фиксации вклада участников

Git позволяет объективно зафиксировать вклад каждого участника:

- **Автор коммита** виден в истории.
- **Сообщение коммита** отражает суть изменения.
- **Pull Request** показывает, какие файлы изменены и кем.
- **Ревью** фиксирует, кто проверял изменения.
- **Merge** показывает, когда изменения попали в основную ветку.

Таким образом, преподаватель и участники команды могут точно определить,
кто и какую работу выполнил.

## 2. Распределение обязанностей по работе с репозиторием

Распределение обязанностей выполнено на основе RACI-матрицы,
разработанной в первой самостоятельной работе.

| Обязанность | R (выполняет) | A (отвечает) |
|---|---|---|
| Создание и настройка репозитория | Руководитель, Архитектор | Руководитель |
| Поддержание структуры папок | Все участники | Руководитель |
| Написание отчётов | Все участники | Руководитель |
| Внесение коммитов | Каждый за свои изменения | Руководитель |
| Проверка Pull Request | Руководитель, Архитектор, Тестировщик | Руководитель |
| Слияние веток (merge) | Руководитель | Руководитель |
| Резервное копирование и актуальность | Все участники | Руководитель |

Подробное описание ролей и обязанностей представлено в документе
`docs/roles-and-responsibilities.md`.
